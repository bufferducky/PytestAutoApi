# 维护业务场景、套件和覆盖账本

R03 继续使用平台为主真源。Cases 页上方是正式场景编辑和覆盖账本，下方旧列表仅为兼容目录；Suites 页上方维护固定版本套件，历史 demo 保留迁移入口。

## 场景编辑

先配置 R02 target/身份/项目，再创建草稿。普通字段包括名称、优先级、模块、标签、目标/身份/绑定、参数schema和默认参数。每个 HTTP 步骤分别维护 ID、阶段、依赖、方法、URL、查询/写入用途、请求体、断言和提取。

阶段按 setup→action→verify→cleanup 排列。读取 `{{outputs.create.id}}` 必须依赖 create，create 的提取目标写 `outputs.create.id`。参数只能从声明的 params 传入，不能用本次参数替换 host/身份。清理按声明关系反序执行，R04 会补资源所有权。

保存草稿后再做发布预检；预检针对已保存内容，不会发业务请求。字段错误包含步骤索引。暂未支持的 fixture/wait 可保存在草稿，但不能发布。普通场景至少有一项必需业务验证，不能只有请求没有断言。

填写变更说明后发布，发布生成不可变版本与hash。继续编辑只修改草稿；再次发布生成v2，不改已有v1与旧run。

## 运行与套件

选择明确发布版本，先计划预览，核对请求/副作用和上下文。Mock 要为 `s0__<step_id>` 配置每步响应；它不会发真实业务请求，也不更新live覆盖。真实运行必须确认每个启用步骤的请求契约，并核对测试资源/写入范围。

套件按顺序引用 scenario_id/version，配置 smoke/core/extended 标签与总预算。它不追随最新版本；各场景参数/输出隔离，清理时恢复对应上下文。套件内参数覆盖按 scenario_id 分组。计划预览和实际运行共用同一编译链路。

## 导入和备份

标准导出包含 schema_version/hash/来源，导入检查完整性并生成新草稿。旧 YAML 只允许 data 下小于等于1MiB文件，导入报告列字段映射、不支持能力、秘密移除及后续整理项，导入不执行任何业务。

旧 demo 的运行、导入与 seed 入口已退役，不再生成演示草稿。旧脚本、业务示例和本地 Allure 报告已移除；平台数据库中的历史证据继续保留。前端粘贴 YAML 的导入能力仍会生成待预检草稿，未映射能力继续显示迁移阻塞。

SQLite版本3引入草稿/发布版本/覆盖账本。迁移前自动生成assets-backup；回退前暂停执行，保留新资产导出和当前数据库，再使用兼容程序或升级前备份，不改版本号强行绕过兼容检查。

## 覆盖账本

点击“导入三端研究账本”只读取本地归档。初始650条是静态观察：中台213处、SaaS346处、App91处，并不是650个在线接口；同一路径不同端/位置的证据保持独立，null字段表示未知而非空请求。

编辑风险、模块、契约状态/依据和场景版本关联后，账本计算近期有效live证据。默认7天；Mock、旧版本、不同hash、过期、被阻塞/跳过或清理失败都不能算当前有效覆盖。分母只使用已确认风险，同时列出全部未确认/未覆盖项，避免假100%。

工作台显示来源文件/hash/位置和确认依据。真实契约仍应在测试环境核对；导入不会替用户猜业务请求体、权限和错误码。

本轮验证为本地HTTP生命周期、真实ASGI接口、仓储/编译及类型构建；真实公司业务在R07，浏览器/设备旅程在R09。
