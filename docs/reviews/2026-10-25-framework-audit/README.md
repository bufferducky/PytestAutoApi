# Bug Analysis: 测试底座已扩展，言迹业务回归与日常使用仍未闭环

审查日期：2026-10-25，Asia/Shanghai。范围：本地当前工作区、测试平台线上页面和查询 API、言迹中台与 SaaS 登录后页面，以及 `docs/reverse-engineering/yanji/` 的 Web/App 研究。代码基线为 `221aba8` 加审查开始时已有的 135 项未提交变更；本报告评估的是这个工作区，不能只用该提交复现全部现状。

**结论：当前平台可以证明部分执行基础设施可用，但还不能承担言迹的日常业务回归。问题主要集中在业务接入缺失、跨层证据失真和工作流难用。现有引擎有可保留的可靠性能力，没有证据支持全部推倒重写。**

本轮登录了两个言迹后台并查看页面，没有执行下发、绑定、删除、录音、分析或财务变更；没有创建线上测试平台资产或运行。复现探针只使用临时 SQLite 和本机 HTTP 服务，没有连接业务数据库。账号、密码、Token 和客户明细不进入交付文件。

证据：[线上查询摘要](online-summary.json)、[本机复现源码](reproduce.py)、[本机复现结果](reproduction-results.json)、[被审查源码 SHA-256](source-manifest.json)。线上摘要采集于北京时间 20:48 左右，是时点快照，不代表后续状态。

### F01：平台的绿色结果尚未覆盖言迹业务

**观察：** 线上 5 个场景草稿：3 个平台自检已发布，2 个旧 demo 未发布且有迁移阻塞；1 个套件只组合平台自检。累计 3 次 live 运行全部访问容器内 `http://127.0.0.1:8000` 的 health、runs、worker/status。另有 1 条已明确标记的历史 Mock，不计 live。

`identity-profiles=0`、`context-bindings=0`；覆盖账本的静态观察、已确认风险和已验证风险均为 0。没有已配置的 center/saas 身份目标，当前 target 的 kind 都是 default。这些自检是真实 HTTP，不能叫作伪造运行；但它们也不能证明言迹登录、权限、录音或下发功能正确。

**历史原因：** [总进度表](../../../.trellis/tasks/10-25-yanji-single-qa-roadmap/progress.md) 明确记录 R07 因资源/契约不足、按此前用户决定暂缓。因此这是已知产品缺口，不能指责为“已经实现的业务用例坏掉了”。真正的问题是日常业务价值仍停在该依赖处，而通用能力继续扩展。

**后果与修复：** 首页“真实测试”只表达传输方式，缺少业务验证范围。增加独立的“平台自检/言迹业务”统计和未接入状态；先交付两个后台的身份＋查询小闭环，再引入写入。不要把测试数量或静态接口数量当作业务覆盖率。

定位：`services/dashboard_service.py:33`、`repositories/run_repository.py:465`；线上实例见 `online-summary.json`。

### F02：上下文预检有假绿路径

**复现：** 本机服务返回 `code=200`，但响应中的 tenant/project 与绑定值不同；target 配置了 `requires_context=true` 和一条已确认查询，却没有填 `tenant_path/project_path`。`ContextTransport.preflight()` 返回 `context=passed`。

**原因：** 只有配置了归属字段才进行比较，最终却只根据 checks 非空来决定 context 是否通过。接口可达与业务码通过，被提升成了项目归属通过。

**后果：** 操作者可能相信当前租户/项目已被验证，从而在错误上下文上继续测试。**这是框架判定缺陷，不是言迹服务端越权证据。**

**根治与验收：** 分开记录 service、authentication、tenant、project 的验证证据；必需归属没有回读证据时返回 not_verified 或阻止进入依赖归属的运行。只配置 code 查询不能获得 context passed；配置完整后，错误 tenant/project 必须失败；不需要上下文的 target 应明确 not_required。

定位：`workers/context_transport.py:104`、`:129`、`:139`；`schemas/context.py:42`。

### F03：运行环境与构建没有从 UI 到结果完整传递

**线上实例：** 套件运行 `be9ecf61c3f34b74940483f92015a1dd` 的 `environment_id=null`、`build=unspecified`；其 target 快照却有明确环境。它已成功，单 run 的 `eligible_for_release=true`。

**原因：** 编辑器 `runData()` 只提交 transport_mode 和 parameters；`AssetRunRequest.environment_id` 可空、build 默认为 unspecified；`AssetService.run()` 将这个可空环境直接传入 `_create_prepared()`，没有从快照派生环境。后者也没有为资产入口补 environment_name。不能把普通 `create_run()` 已有环境处理，等同于所有入口都正确。

**后果：** 按环境筛选会遗漏这条运行；无法精确定位被测构建；单 run 的 eligible 命名容易被误读为业务发布许可。现有严格发布报告会因缺构建/业务证据阻止放行，**本轮没有证明 strict 门禁已被绕过**。

**根治与验收：** UI 提交实际 build；服务端从固定目标推导单环境并交叉校验，混合环境显式建模或拒绝；运行保存环境名称/配置快照；将执行证据可用性与发布判定分开命名。验证必须走浏览器默认提交入口，随后按环境筛选能找回运行。

定位：`ScenarioAssetsPanel.vue:217`；`schemas/assets.py:75`；`services/asset_service.py:133`、`:226`；`repositories/run_repository.py:317`。

### F04：开发仓库能力与发布产物不一致

**静态证据：** `AssetService.import_research()` 固定读取三份 `docs/reverse-engineering/yanji/...` JSON；legacy 导入读取 `data/`；媒体校验读取 `Files/test-media/`。当前 Dockerfile 只复制 pyproject/README、src、backend src 和 Alembic；Compose 只挂载状态卷，没有挂这些业务资产目录。

**后果：** 按当前 Dockerfile 构建的镜像无法执行研究导入，缺文件会沿未转换的异常链返回错误；旧 YAML 导入和媒体登记同样缺少交付来源。本轮没有点击线上导入按钮，未把推断冒充线上报错。

**根治与验收：** 研究数据采用经过筛选的版本化 bundle 或显式上传；媒体采用受控上传/挂载；旧 YAML 提供导入文件入口或明确停用。界面根据部署能力展示入口。用干净发布镜像验收一次导入和缺失时的可读错误，不能只在完整源码树上验证。

定位：`deploy/Dockerfile:5`、`deploy/compose.yaml`；`services/asset_service.py:251`、`:347`；`services/evaluation_service.py:51`。

### F05：环境、目标与密钥配置未闭环

**线上观察：** “默认联调环境”显示 online、鉴权说明为账号密码＋Token；对应迁移 target 的 auth.mode 却是 none、requires_context=false、登录契约未确认。这里的 online 是人工状态，不是本轮健康或鉴权验证。

**设计断层：** environment 和 target 都保存地址与鉴权相关内容；target 是独立快照、不随 environment 更新，这是现有规范中的有意设计。UI 却没有充分解释两者关系，容易出现改了环境、实际请求仍走旧 target 的误解。

凭证只支持服务端 `env:PYTA_SECRET_*`，这比明文写入用例好。但当前 Compose 未声明任何这些变量的注入来源，UI 也无法实际配置秘密。只在表单填一个 ref 并不能让容器取得凭证。后端运行时是否被手工另加变量未核验；不能据此声称服务器一定没有秘密变量。

**根治与验收：** environment 管生命周期，target 管具体系统及认证策略；UI 显示实际生效快照和差异。补受限密钥注入/轮换说明、就绪检查与可读缺失提示；保留秘密引用。online 与“最近验证通过”分开。以在空白部署中配置两个真实查询目标为验收路径。

定位：`services/context_service.py:29`、`:162`；`workers/context_transport.py:24`；`ContextProfilesPanel.vue`；`EnvironmentsPage.vue`；`deploy/compose.yaml:35`。

### F06/F07：日常操作成本高，核心请求编辑却不完整

线上用例页从上到下堆叠：场景编辑、覆盖账本、资源定义/资源池/媒体、Web/Android 旅程、AI 历史、用例目录。列表与编辑器同时出现，新用户需要先理解 target、identity、binding、revision、发布版本、fixture、risk、build 等大量概念；多个关联仍要求手工复制 ID 或 JSON。

页面外壳有统一样式，内部按钮、列表、表格、JSON 输出和操作密度不一致；新建/查看/高级维护的主次不清。底部还保留面向开发者的“第一阶段/后续扩展点”文字。仅修正手机宽度不能解决这类信息结构问题。

`ScenarioAssetsPanel` 的新步骤只可设置 method/url/body；没有 headers、query 参数、body_type/form/file 的普通编辑入口。已有导入步骤的 request 字段会被保留，**不是保存一定丢字段**；问题是从新建表单无法完成很多实际接口，且没有根据响应选取字段的提取工作流。

**建议工作流：** 先选系统/身份/项目 → 填请求 → 在安全测试范围内调试 → 从响应建立断言/提取 → 保存 → 加入套件 → 查看执行。资源/覆盖/设备/评测进入单独页面或高级区；引用优先用可搜索选择器，JSON 保留为高级入口。

**验收：** 不写 JSON、不复制数据库 ID，就能创建两个后台的普通 GET/POST 查询场景，设置 headers/query/JSON 或 form 请求，加入套件并在结果页看到业务名称。复杂 fixture 可保留高级配置，无需另造全能低代码系统。

定位：`pages/CasesPage.vue:3`、`components/ScenarioAssetsPanel.vue:17`、`:173`、`:214`；`pages/SuitesPage.vue:50`；`pages/EnvironmentsPage.vue:165`。

### F08：测试绿灯和实际交付验收不在同一条路径

本轮 `.venv/bin/python -m pytest tests -q` 为 **260 passed / 9 skipped**。7 个跳过依赖独立 MySQL 验证库，2 个依赖显式浏览器开关。Ruff 和前端类型检查/生产构建通过。

但 `pytest.ini` 的默认 testpaths 仍是 `test_case/`，新架构测试在 `tests/`。旧目录还存在自动登录 fixture。直接运行默认 pytest 并不是这次执行的离线新架构检查；本轮没有运行旧测试，避免触发业务请求。

本轮默认新架构检查没有验证 MySQL 与两个真实浏览器集成；有针对性的本地 HTTP、ASGI、故障注入等有效测试，应保留。问题是这些测试仍漏掉了本报告的三个反例，不能把 260 通过外推成公司业务、干净镜像或端到端 UI 验收完成。

**根治与验收：** 给出唯一清晰的离线检查入口；旧业务测试显式命名并独立授权运行；为 F02/F03/F09 补真正经过生产调用链的回归；发布门槛单列隔离 MySQL、浏览器关键路径、干净镜像检查的执行/跳过状态。MySQL 测试会清表，只能用现有保护要求的独立验证库，不能复用业务测试连接。

定位：`pytest.ini:3`、`test_case/conftest.py:67`、`tests/backend/test_mysql_storage.py:13`、`tests/backend/test_platform_frontend_browser.py:17`、`tests/backend/test_browser_journey_integration.py:13`。

### F09：插件声明被静默丢弃

**复现：** 同一已发布场景，一份步骤配置 `plugin_refs=[]`，另一份为 `['bootstrap-auth@1']`，两者都可编译；去掉随机 run_id 后编译定义完全一致。`preflight()` 的插件版本表接受此值，`compile_scenario()` 没有传递它；worker 根据 context_snapshots/auth_bootstrap 另行选择插件。

**后果与根治：** 发布成功会让操作者误以为声明已生效。要么实现从引用到受控执行器的契约，要么明确拒绝当前不可用的插件声明。用能观察插件效果的测试验收，不能只测版本字符串合法。

定位：`services/scenario_compiler.py:13`、`:117`、`:209`；`workers/runner.py:265`。

### F10：草稿编辑与发布之间缺少明确状态提示

修改本地表单后，预检/发布仍针对服务端已保存的 selected/revision，页面没有 dirty 状态，也没有在未保存时锁定发布或显示“当前检查的是哪个草稿”。切换条目没有处理未保存编辑的提示；newDraft 也没有重置全部上下文和参数表单状态。

这不证明每次发布都会错误；风险是用户以为在检查屏幕上最新内容，实际处理的却是上次保存值。套件新建仍靠 ID＋版本录入，计划和预检主要输出 JSON，使用者很难察觉差异。

**验收：** 未保存变更清楚可见；预检/发布只能针对明确 revision，或要求先保存；切换条目有明确处理；新增时不继承上一条身份/目标/运行参数等未预期状态。结果中可展开请求实际版本。

定位：`ScenarioAssetsPanel.vue` 的 `newDraft/select/preflight/publish/runData`。

### F11：UI/App/AI 的实际能力缺口应从主操作中显露

线上能力返回 Playwright 未安装、Appium 未安装、adb 不可用，W01—W04/A01—A04 均未验证；页面保留创建旅程表单。AI 新执行已禁用、历史仍可查，这个诚实边界应保留。不能根据存在表单或 runner 代码宣称支持线上浏览器、真机或模型质量回归。

App 历史材料是 APK 静态分析；不代表当前 App 已跑通。SaaS 本次可见菜单较旧报告新增“业绩中心”，说明旧静态账本还要处理版本漂移。没有深入检查该新增菜单，不给出其覆盖结论。

**下一步：** 主界面直接显示“未配置/缺驱动/尚未接入”，隐藏不可用主操作或提供准备步骤；API 回归成熟后，先补一条 Web 接诊列表—详情—结果链路，再根据实际设备条件推进 App。AI 单独准备合成/脱敏数据和人工评价基准，不能用 code=200 或关键词命中代替质量。

### F12：复杂度增长快于业务反馈

`ReleaseService` 内固定 S01—S16 和 Web/App 风险编号；普通 API 回归也受同一政策影响。这里阻止“暂缓业务被当作通过”是有意且正确的，后续应把政策定义放入明确版本的业务回归包，而不是删掉这些阻断。

API、调度和执行器在单进程中运行，一个执行槽；MySQL 写事务还使用同一 write_guard 行串行。对个人工作台可作为明确限制保留，但媒体长任务会占槽，需要队列/忙碌/预计等待反馈。覆盖汇总会读取大量运行并逐风险、逐引用查明细；没有性能压测，本轮不声称已有线上性能事故。

多个 service 直接操作仓储内部连接或其他服务内部方法，`MemoryWorkerRunner` 等命名与实际持久存储语义不一致；根 README/requirements 仍主要讲旧框架，pyproject 则是新栈。维护者容易走错入口。

**建议：** 保留单体和现有引擎，先把上下文/编译/证据契约收紧；业务包负责风险与发布政策；执行器只负责执行与结果。统一新旧入口说明，在真实负载出现后再决定并发/查询优化，当前没有引入微服务或重型队列的证据基础。

### F13：关键知识在本机存在，却未随 Git 交付

`git check-ignore -v` 确认用户全局忽略配置将 `docs/` 和 `.trellis/` 排除。审查前，仓库只跟踪 1 份 docs 文件、2 份 `.trellis` 前端规范文件；言迹逆向材料、绝大多数后端规范和业务任务规划均未被 Git 跟踪。文件在本机真实存在，不能说资料不存在；但克隆仓库、CI 或其他开发机不会自然取得这些知识。

这也解释了为何只按 git status 可能看不见重要新增文档，以及为什么部署脚本没有天然携带业务研究输入。现有 135 项未提交实现意味着仅靠 HEAD 也无法复现当前线上/本地行为；这是一项交付限制，不据此推断正在进行的改造应立即整体提交。

**建议与验收：** 明确可入库的脱敏研究、规范、任务设计与运行证据目录，使用仓库级选择性规则或精确 force-add；保留密码、运行状态库、客户数据和大体积原始产物的忽略。用干净 checkout 核查规范索引能打开、测试和发布资源齐全。本轮只将本次审查文件及修改的规范/模板精确加入，不全量纳入历史资料。

## 2. Why Fixes Failed (if applicable)

本轮是审查，没有执行产品修复，也没有把探针脚本调试算作产品修复史。以下来自现存规划和代码边界，描述“为什么继续增加能力仍不能完成用户目标”，不臆测过去开发者的动机。

1. **范围扩展未跨过业务依赖。** R07 已暂缓，R08—R10 可以完成本地机制，但它们不能补回缺失的真实业务事实。需要先恢复一个小业务闭环。
2. **传输真实性代替业务有效性。** 删除 Mock fallback、标记演示历史都很有价值；但真实调用平台自身接口，只能证明平台自检。
3. **单层修复没有传播到所有入口。** 普通 run 的环境处理、预检 checks 的业务码、插件字符串注册都分别存在；从 UI 到资产入口、从服务可达到归属判定、从注册到执行仍有断点。
4. **源码树验收代替发布产物验收。** 本地研究导入可读到 docs，不代表 Docker 内也有同一份资料。
5. **布局修复代替工作流设计。** 响应式规范与已有修复应保留；页面不溢出以后，还需要降低主路径中的概念和录入负担。

## 4. Systematic Expansion

### 4.1 言迹需求与现有能力对照

| 实际业务 | 所需验证 | 当前证据与缺口 |
|---|---|---|
| 中台与 SaaS 身份 | 各自登录、用户/角色、菜单/按钮、令牌到期、固定项目归属 | 浏览器可登录；平台没有身份/绑定资产或相应业务运行 |
| 中台模板/质检/标签下发 | 内容/版本、目标/非目标项目、覆盖规则、重复/冲突和恢复 | 已有研究与可见入口；没有平台 live 回归 |
| SaaS 接诊与录音 | 精确对象的列表/详情/关联、绑定/解绑、异步分析、异常及清理 | 本次看见接诊分析状态与关联录音；未做写入/详情链验证 |
| 项目内规则/偏好 | 工牌/线上分析分支、匹配规则、必填配置及作用范围 | 菜单和页面存在；平台未连接实际场景 |
| 人设/评估包 | 精确筛选、绑定对象/章节、负向及恢复 | 只有未发布的历史迁移草稿；不能以当前账号不可见扩展模块冒充已测 |
| App | 指定 APK/设备上的登录、录音、播放、结果与权限 | 只有历史静态分析；线上没有驱动/设备证据 |
| AI/语音质量 | 事实准确、章节完整、标签/质检符合业务、ASR 等专项 | 新评估禁用；尚无真实模型及校准证据 |
| 产品订单、财务、日报 | 状态与一致性、计费/推送边界、失败处理 | 研究中有模块线索；本轮未开展，不纳入首轮写入回归 |

### 4.2 应保留的能力与排除的误判

- 历史 Mock 明确标记并排除 live 统计，新模拟/新评估执行被拒绝；不是继续用 Mock 伪装言迹验证。
- 已有版本冻结、依赖阻塞、有限轮询、结果/清理记录、秘密引用与脱敏、任务认领及中断对账，适合继续修正和复用。
- strict 发布报告保留未验证业务风险，比账本为空就全绿合理；修复应保留此性质。
- 资料中的静态请求表达式、已浏览页面、在线接口测试通过是三个不同量。旧报告中因拦截 POST 导致的空列表，不作为言迹后端故障证据。
- 单实例对个人工作台不是天然错误；本轮没有性能压测、渗透测试、生产写入或数据库核查，相关问题不越界下结论。
